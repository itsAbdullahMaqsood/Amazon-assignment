## Two decisions worth knowing

**OrderClient wraps both sections, not just the right one.** Your spec says to wrap "the section that changes", but paying flips the badge in `OrderInfo` (left column) too. Wrapping only the right column would leave a red unpaid badge next to a paid order until reload.

**Variant matching uses the line's stored image, not its colour.** The seeder assigns each variant a random hex from a list of 7, so two variants of the same product can share one — a colour-only match would decrement the wrong variant's stock. `line.image` is that variant's own first image, so it identifies it exactly. Colour and size-presence remain as fallbacks.

## Known limits

- **`Product.product` needs populating to link out.** Order lines store no slug (same as cart lines), so both the page query and the payment response populate `products.product` with `slug`. If you ever read an order without that populate, the product links go to `/product/`.
- **Payment is not transactional.** The order is marked paid, then stock is decremented, then the Cart is deleted. If the process died between those steps you'd get a paid order with partial stock changes. The already-paid guard prevents double-application on retry, but there's no rollback. Fine for a simulated payment; a real gateway would want a transaction or an idempotency key.
- **Admins can view any order but not pay one** — the payment handler is owner-only.
